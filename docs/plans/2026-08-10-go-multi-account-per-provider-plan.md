# Go Multi-Account Per Provider Implementation Plan

## Status

Proposed - not yet implemented.

## Objective

Allow onWatch to discover, poll, persist, query, and report several accounts for
each bundled CLI-backed provider type:

- Codex
- Anthropic
- Antigravity

Codex already supports multiple accounts and must remain compatible. The primary
Go work is to add equivalent support for Anthropic and Antigravity without
copying their credentials into SQLite or mixing telemetry between accounts.

MiniMax is not part of this delivery, but its database-backed manager is a useful
precedent. Other single-account providers remain out of scope until they have a
defined multi-account credential contract.

Container credential layout and login selection are specified separately in:

- `docs/plans/2026-08-10-agent-multi-profile-design.md`
- `docs/plans/2026-08-08-antigravity-multi-account-design.md`

## Provider Constraints

### Codex

Codex profiles contain stable provider account and user identifiers. Team and
Business accounts can share a provider account ID across users, so deduplication
must continue to use the existing composite account/user identity logic.

The first implementation should preserve `/data/codex-profiles` as the Codex
source of truth. Moving Codex to native `/auth/codex/<name>/auth.json`
directories is a separate migration after Anthropic and Antigravity reach
feature parity.

### Anthropic

Named accounts can be polled through the OAuth usage API using separate Claude
credential files. Each account must have an independent credential reader and
writer because Anthropic refresh tokens rotate and must be saved immediately.

The statusline bridge is a single shared file generated by the locally running
Claude Code process. It has no account identity. Therefore:

- `default` may use `auto`, `statusline`, or `api` behavior.
- Named accounts use the API path only.
- A statusline snapshot must never be copied into every named account.
- `statusline` mode with only named accounts is a configuration error, not a
  silent fallback.

The current credentials do not expose a stable account identifier in the parsed
Go structure. Until a stable provider identity is verified, Anthropic accounts
are canonicalized by validated local alias and are not automatically deduplicated
across aliases.

### Antigravity

Antigravity has no native profile or config-directory option. Each account needs
a complete `HOME`, including its `.gemini`, `.codeium`, cache, and GNOME Keyring
state.

Only managed CLI mode supports several named accounts concurrently. The IDE
probe and a manually supplied base URL identify one external language-server
session and therefore belong only to `default`. Named accounts must never all
fall back to that same IDE/manual connection.

Every managed runner must use the same UID as onWatch because port discovery
walks the child process tree and reads `/proc/<pid>/fd`. Separate Unix users
would make those descriptors unreadable without running the daemon as root.

The CLI is memory-heavy. Multi-account polling must be serialized, staggered,
and non-warm until measurements prove a larger concurrency limit safe.

## Design Principles

1. `provider_accounts.id` is the canonical internal account ID everywhere.
2. Account IDs are global database IDs. Only Codex may assume legacy ID `1`.
3. Credentials remain in provider auth files/keyrings, never in new DB metadata.
4. A local account name is an alias; a provider external ID is the deduplication
   key when one is available.
5. Every snapshot, cycle, notification, metric, session, and HTTP query carries
   an account context.
6. An omitted account parameter resolves to the provider's actual `default`
   account. An invalid supplied account parameter returns an error rather than
   silently selecting another account.
7. Removing credentials stops polling and soft-deletes the account record while
   preserving historical telemetry.
8. Invalid or temporarily unreadable credentials do not imply account deletion.
9. Manager shutdown waits for all account goroutines and child processes.
10. Logs include provider, account alias, and numeric account ID but never tokens.

## Proposed Go Architecture

### Account definitions

Add a small provider-neutral package:

```text
internal/account/
|-- account.go
|-- names.go
|-- source.go
`-- source_test.go
```

Core types:

```go
type Definition struct {
    Provider   string
    Name       string
    AuthRoot   string
    ExternalID string
    Metadata   map[string]string // non-secret display data only
}

type Source interface {
    Provider() string
    List(context.Context) ([]Definition, error)
}
```

`ValidateName` enforces `[a-z0-9][a-z0-9_-]{0,31}`. Directory-backed sources
must reject symlinks and confirm every resolved account path stays below the
configured provider root.

The source reports account membership, not credential modification time.
Provider agents already re-read mutable credentials. This avoids restart loops
when an agent writes a rotated refresh token or Antigravity updates its keyring.

### Account supervisor

Add a reusable lifecycle component in `internal/agent/account_supervisor.go`:

```go
type AccountInstance struct {
    Definition  account.Definition
    DBAccountID int64
    Cancel      context.CancelFunc
}

type AccountRunnerFactory interface {
    Build(context.Context, account.Definition, int64) (AgentRunner, error)
}
```

The supervisor owns:

- initial discovery;
- provider-account reconciliation;
- start-on-add;
- cancel-on-remove;
- soft deletion of confirmed orphans;
- per-account polling checks;
- reload requests;
- periodic membership scans;
- panic containment;
- `sync.WaitGroup` shutdown;
- stable, sorted status reporting.

Provider-specific managers wrap the supervisor and supply credential validation,
runner construction, and resource policies. Do not migrate Codex to the shared
supervisor in the first change; use Codex tests as the behavioral contract and
adopt the shared component only after Anthropic and Antigravity are stable.

### Account source implementations

Implement:

```text
internal/account/anthropic_source.go
internal/account/antigravity_source.go
```

Anthropic source:

- Scans `<auth-root>/<name>/.claude/.credentials.json`.
- Lists only valid directory names.
- Leaves malformed credential files visible as unhealthy accounts rather than
  deleting their DB records.
- Does not expose token data through `Definition`.

Antigravity source:

- Reads an explicit, validated account list or secret-free account manifest.
- Resolves each name to `<auth-root>/<name>`.
- Does not attempt to inspect or extract keyring secrets.
- Treats directory scanning alone as insufficient proof of authentication.

An explicit Antigravity list is preferred because verifying an account requires
launching the large CLI and empty directories can remain after an aborted login.

## Storage Changes

### Provider account helpers

Move the provider-neutral `ProviderAccount` type and helpers out of
`internal/store/codex_store.go` into `internal/store/provider_accounts.go`.
Preserve function signatures during the move.

Add:

```go
func (s *Store) EnsureDefaultProviderAccount(provider string) (*ProviderAccount, error)
func (s *Store) ResolveProviderAccount(provider string, accountID int64) (*ProviderAccount, error)
func (s *Store) ResolveDefaultProviderAccount(provider string) (*ProviderAccount, error)
```

`ResolveProviderAccount` must verify that the numeric ID belongs to the requested
provider. This prevents a valid MiniMax account ID from being accepted by an
Anthropic endpoint.

### Schema migration

For both `anthropic` and `antigravity`:

1. Insert or resolve the provider's `default` row without assuming its ID.
2. Add `account_id INTEGER NOT NULL DEFAULT 0` to snapshots.
3. Add `account_id INTEGER NOT NULL DEFAULT 0` to reset cycles.
4. Backfill legacy rows from `0` to the resolved provider default ID inside one
   transaction.
5. Add account-first indexes.

Required indexes:

```sql
CREATE INDEX IF NOT EXISTS idx_anthropic_snapshots_account
  ON anthropic_snapshots(account_id, captured_at DESC);

CREATE INDEX IF NOT EXISTS idx_anthropic_cycles_account
  ON anthropic_reset_cycles(account_id, quota_name, cycle_start DESC);

CREATE INDEX IF NOT EXISTS idx_antigravity_snapshots_account
  ON antigravity_snapshots(account_id, captured_at DESC);

CREATE INDEX IF NOT EXISTS idx_antigravity_cycles_account
  ON antigravity_reset_cycles(account_id, model_id, cycle_start DESC);
```

Child quota/model-value tables remain connected through `snapshot_id`; they do
not need a duplicate `account_id` column. Every join must filter through the
parent snapshot's account ID.

Migration tests must start from both a legacy database and a current database,
run migration twice, and prove that no historical row changes account on the
second run.

### API model changes

Add `AccountID int64` to:

- `api.AnthropicSnapshot`
- `api.AntigravitySnapshot`
- `store.AnthropicResetCycle`
- `store.AntigravityResetCycle`
- account-specific usage point/result types where the caller needs identity

Provider response conversion leaves `AccountID` unset. The account agent assigns
its DB account ID before inserting or processing the snapshot.

### Store signature changes

Make account ID mandatory on all Anthropic and Antigravity store operations.
Examples:

```go
QueryLatestAnthropic(accountID int64)
QueryAnthropicRange(accountID int64, start, end time.Time, limit ...int)
QueryActiveAnthropicCycle(accountID int64, quotaName string)
QueryAnthropicCycleHistory(accountID int64, quotaName string, limit ...int)
QueryAnthropicUtilizationSeries(accountID int64, quotaName string, since time.Time)

QueryLatestAntigravity(accountID int64)
QueryAntigravityRange(accountID int64, start, end time.Time, limit ...int)
QueryActiveAntigravityCycle(accountID int64, modelID string)
QueryAntigravityCycleHistory(accountID int64, modelID string, limit ...int)
QueryAntigravityUsageSeries(accountID int64, modelID string, since time.Time)
QueryAntigravitySnapshotAtOrBefore(accountID int64, t time.Time)
```

Also scope:

- cycle overview queries;
- latest-per-quota queries;
- grouped Antigravity cross-quota queries;
- model/quota-name discovery;
- retention or cleanup statements;
- exports and metrics queries.

Avoid variadic account parameters or implicit `1` fallbacks in store methods.
Callers must resolve the correct provider default explicitly.

## Tracker Changes

Trackers should use `snapshot.AccountID`, following `CodexTracker`:

```go
func (t *AnthropicTracker) Process(snapshot *api.AnthropicSnapshot) error
func (t *AntigravityTracker) Process(snapshot *api.AntigravitySnapshot) error
```

Internally, every cycle lookup/update receives `snapshot.AccountID`.

Update reset callbacks to carry account context:

```go
type ResetEvent struct {
    Provider  string
    AccountID int64
    QuotaKey  string
}
```

Replace provider-specific `func(string)` callbacks incrementally with
`func(ResetEvent)`. This prevents reset notifications for one account from being
deduplicated against another.

`UsageSummary` and every tracker read helper must accept `accountID` explicitly.

## Anthropic Implementation

### Credential store abstraction

Replace ambient global credential access inside account agents with:

```go
type AnthropicCredentialStore interface {
    Load(context.Context) (*AnthropicCredentials, error)
    Save(context.Context, AnthropicCredentials) error
}
```

Implement:

- `ClaudeFileCredentialStore` for named container accounts;
- `DetectedAnthropicCredentialStore` as the backward-compatible default adapter
  around current Keychain/keyring/file detection;
- `StaticAnthropicCredentialStore` for `ANTHROPIC_TOKEN`, with no refresh-token
  persistence.

The file implementation must preserve the existing atomic write, backup,
permissions, and unknown JSON fields. It takes an explicit file path and never
calls `os.UserHomeDir`.

### Agent changes

Add `accountID` and `accountName` to `AnthropicAgent`. Replace separate token and
credential refresh callbacks with the injected credential store.

Before each API poll:

1. Load the matching account's credentials.
2. Update only that agent's client token.
3. Refresh expiring credentials if possible.
4. Save rotated access and refresh tokens immediately through the same store.
5. Retry the API call with the refreshed token.

All notifications and logs include the account context. Each account uses a
session key generated by a shared helper:

```go
AccountSessionProvider("anthropic", accountID) // anthropic:<id>
```

### Anthropic manager

Add `internal/agent/anthropic_agent_manager.go`.

The manager:

- starts one API agent per discovered named account;
- preserves the existing default-account behavior when no auth root is set;
- attaches the statusline bridge only to `default`;
- applies global and `anthropic:<id>` polling settings;
- exposes `Reload` and `GetRunningAccounts`;
- does not automatically deduplicate aliases until a stable external ID exists.

## Antigravity Implementation

### Runner environment

Add explicit options to `AntigravityCLIRunner`:

```go
func WithAgyHome(string) AntigravityCLIRunnerOption
func WithAgyRuntimeDir(string) AntigravityCLIRunnerOption
func WithAgySessionFactory(AgySessionFactory) AntigravityCLIRunnerOption
func WithAgyWarmTTL(time.Duration) AntigravityCLIRunnerOption
```

Build `cmd.Env` by overriding `HOME`, `XDG_RUNTIME_DIR`, relevant XDG roots, and
`DBUS_SESSION_BUS_ADDRESS` for the account. Preserve current behavior when no
options are supplied.

The session factory starts a fresh D-Bus and GNOME Keyring session for the
account and returns its environment plus a cleanup function. The bus address is
kept only in memory or the temporary runtime directory, never in the persistent
auth volume.

The runner remains the direct parent of `agy`, or otherwise preserves descendant
port discovery and cancellation. Tests must prove `discoverPorts` still sees the
language-server child.

### Agent changes

Add `accountID`, `accountName`, and an injected CLI runner factory to
`AntigravityAgent`. Assign `snapshot.AccountID` before storage and tracking.

Source policy:

- `default` may use `ide`, `cli`, `both`, or manual connection behavior.
- Named accounts are forced to `cli`.
- A named account never falls back to IDE/manual after CLI failure.
- Manual base URL remains single-account until per-account connection metadata
  is explicitly designed.

### Antigravity manager

Add `internal/agent/antigravity_agent_manager.go`.

The manager:

- starts one agent per declared account;
- uses email returned by `GetUserStatus`, normalized to lowercase, as the
  external identity when available;
- reconciles duplicate external identities without deleting history;
- shares a size-one semaphore across all CLI account polls;
- sets CLI warm TTL to zero when more than one CLI account is active;
- staggers first polls across the configured interval;
- stops and cleans up each runner/session on removal or shutdown;
- applies global and `antigravity:<id>` polling settings.

Do not hold the semaphore while waiting for the next ticker. Acquire it only for
runner startup, readiness, quota fetch, and teardown.

## Main Wiring and Configuration

Add config fields for provider auth roots and Antigravity account membership:

```go
AnthropicAuthRoot    string
AntigravityAuthRoot  string
AntigravityAccounts  []string
```

Container defaults come from the container contract; host defaults preserve
current single-account detection unless the user opts into an auth root.

Refactor duplicated settings parsing in `main.go` into:

```go
func providerPollingEnabled(store *store.Store, provider string) bool
func accountPollingEnabled(store *store.Store, provider string, accountID int64) bool
func accountSessionProvider(provider string, accountID int64) string
```

Replace the single `anthropicAg` and `antigravityAg` registrations with their
managers. Each manager still implements `AgentRunner`, so the outer
`AgentManager` contract does not change.

Startup compatibility rules:

- No auth root or account list: preserve the current single default agent.
- Auth root present: manager mode is enabled even if no ambient token was found.
- Saved named accounts can bootstrap their provider without an environment token.
- A bad account logs an account-scoped health error but does not prevent other
  accounts or providers from starting.

## HTTP and Handler Changes

Add generic account resolution helpers in `internal/web/account_handlers.go`:

```go
func (h *Handler) parseProviderAccountID(r *http.Request, provider string) (int64, error)
func (h *Handler) listProviderAccounts(w http.ResponseWriter, r *http.Request)
```

Recommended endpoint:

```text
GET /api/provider-accounts?provider=anthropic
GET /api/provider-accounts?provider=antigravity
```

Responses contain non-secret data only:

```json
{
  "accounts": [
    {
      "id": 4,
      "name": "work",
      "provider": "anthropic",
      "deletedAt": null,
      "running": true,
      "health": "ok"
    }
  ]
}
```

Update current, history, cycles, summary, insights, sessions, cycle overview, and
logging-history handlers to accept `account_id` for Anthropic and Antigravity.

Rules:

- Missing `account_id`: use the provider's resolved default.
- Supplied invalid/non-numeric ID: HTTP 400.
- ID belonging to another provider: HTTP 404.
- Deleted account with retained history: readable for historical endpoints but
  excluded from active current polling views by default.
- `account_id=all`: handled only by explicit aggregate endpoints or response
  builders; never passed into store queries as a magic numeric value.

Keep existing Codex and MiniMax endpoints as compatibility aliases until the UI
uses the generic account-list endpoint.

## Sessions, Notifications, and Metrics

### Sessions

Keep the current `provider:<account-id>` session encoding for this delivery to
avoid an unrelated session-table migration. Centralize encoding and parsing so
Codex, MiniMax, Anthropic, and Antigravity behave identically.

Default-account handlers also read legacy plain provider sessions for backward
compatibility.

### Notifications

Set both account ID and account name on quota and authentication alerts. Include
the account ID in deduplication keys even for the provider's default account.
The current special case that treats numeric account `1` as the universal
default must be removed because account IDs are global.

Reset callbacks must also carry account ID so one account's reset does not clear
or suppress another account's alert.

### Prometheus metrics

Change Anthropic and Antigravity scrapers to follow the Codex/MiniMax pattern:

1. Query provider accounts.
2. Export `onwatch_account_info` for each account.
3. Query the latest snapshot by numeric account ID.
4. Label quota, freshness, error, and balance metrics with that ID.
5. Remove stale label sets when accounts disappear or are deleted.

## Delivery Phases

Tests first:

- name validation and path containment;
- deterministic source ordering;
- supervisor add/remove/reload behavior;
- invalid credentials do not cause soft deletion;
- clean cancellation and no goroutine leaks;
- provider/account settings fallback.

- extract account polling/session key helpers;
- leave existing Codex/MiniMax behavior unchanged.

### Phase 2 - Account-scoped persistence

Tests first:

- legacy schema backfill to each provider's real default row;
- idempotent migration;
- insert/latest/range isolation;
- cycle isolation;
- overview and cross-quota isolation;
- deleted-account history retention;

Tests first:

### Phase 5 - HTTP, settings, notifications, and metrics

Tests first:

- account listing contains no credential data;

- invalid and cross-provider IDs;
- aggregate response separation;
- per-account polling toggles;

Implementation:

## Test Matrix

| Layer | Required cases |
|---|---|
| Account source | valid, invalid, missing, unreadable, symlink, traversal, sorted output |
| Supervisor | add, remove, restore, failed build, panic, reload race, shutdown |
| Migration | empty DB, legacy DB, populated DB, repeat migration, rollback on failure |
| Store | account-isolated latest, history, cycle, summary, joins, retention |
| Anthropic auth | per-file read, atomic write, rotating refresh token, corrupt JSON |
| Anthropic agent | one paused account does not pause another; statusline only on default |
| Antigravity runner | env isolation, process discovery, session cleanup, serialization |
| HTTP | default resolution, explicit account, wrong provider, deleted history, all accounts |
| Notifications | same quota on two accounts produces independent alert state |
| Metrics | stable labels, deleted account cleanup, account info mapping |
| Race | concurrent reload, polling, refresh write-back, and manager shutdown |

All Go tests must use temporary directories, fake clients/runners, and local HTTP
servers. Unit tests must not read real user credential stores or launch installed
provider CLIs.

## Verification

Use repository commands only:

```bash
./app.sh --smoke
./app.sh --test
```

Before merging each phase:

- run migration tests against a copied legacy fixture;
- run the full suite with race detection through `app.sh`;
- verify no logs contain tokens or raw credential JSON;
- inspect all SQL references to the migrated tables for missing account filters;
- verify the default single-account setup produces the same dashboard data as
  before the migration;
- measure Antigravity memory with two accounts and record the result in
  `docs/WITH_USER_ENV.md`.

## Rollout and Compatibility

1. Ship schema and default-account wiring before enabling account discovery.
2. Keep all existing environment variables and single-account behavior.
3. Enable Anthropic manager mode only when a provider auth root is configured.
4. Enable Antigravity manager mode only when an account list/manifest is present.
5. Keep legacy Codex profiles and provider-specific HTTP endpoints.
6. Mark removed accounts deleted; never delete historical snapshots automatically.
7. Provide a rollback path that ignores additional accounts but can still read
   the backfilled default account.

## Completion Criteria

The implementation is complete when:

- Codex, Anthropic, and Antigravity can each run at least two account agents.
- Every stored and returned datum is associated with the correct provider account.
- Anthropic refresh-token rotation is isolated and durable per account.
- Antigravity sessions are isolated by home/keyring and remain within the memory
  budget through serialized polling.
- Global and per-account polling settings work for all three providers.
- Sessions, notifications, metrics, and every dashboard API preserve account
  identity.
- Removing an account stops polling without deleting history.
- Existing single-account installations migrate without manual database changes.
- `./app.sh --smoke` and `./app.sh --test` pass.

## Decisions Required Before Coding

1. Should Antigravity accounts be declared by `ANTIGRAVITY_ACCOUNTS` or by a
   secret-free manifest inside its auth root?
2. Is alias-only identity acceptable for Anthropic until a stable provider ID is
   verified?
3. Should named Anthropic accounts be rejected when `ANTHROPIC_SOURCE=statusline`,
   or should the manager automatically force those accounts to API mode with a
   warning?
4. Should the generic account endpoint be introduced immediately, or should the
   first release add provider-specific Anthropic and Antigravity endpoints?
5. Is provider-level credential-volume isolation sufficient, as assumed by the
   container design, or is a named volume required for every account?
